## 구현 범위

기존 `BattleSummaryBuilder`와 `BattleSettlementSummaryBuilder`가 Quest 영구 진행의 입력으로 사용할 다음 사실을 정확히 투영하는지 전용 EditMode 테스트로 고정했다.

- 개인 `kills`, `supportKills`, `bossKills`
- 팀 `monsterKills`
- `finalWave`, `result`, `mapId`, `abandoned`
- `(battleSessionId, runtimeMonsterId)` 기준 중복 제거
- 같은 `monsterSpecId`의 서로 다른 Runtime Monster 집계
- 외부 Session 및 roster 밖 Killer/Support 거부
- `FAILED` 매치에서 미완료 Wave 중 확정된 실제 Kill 포함
- `abandoned=true` 참가자의 실제 전투 통계는 제거하지 않고 flag와 함께 보존
- Wave 80 `VICTORY`의 Boss Kill 포함

테스트가 기존 구현을 그대로 통과했으므로 Battle Runtime 수정은 하지 않았다. 특히 `SpawnWave > finalWave`인 Kill을 제거하는 필터를 추가하지 않았다.

## 정책 핵심 검증

`FAILED`, `finalWave=69`인 Summary에 `spawnWave=70`에서 State Authority가 확정한 Kill을 넣었을 때 다음을 확인했다.

- Settlement `result=DEFEAT`
- Settlement `finalWave=69`
- 개인 Kill 증가 유지
- `monsterKills`에 Wave 70 실제 Kill 유지

즉 `finalWave`는 마지막 완전 클리어 Wave이고, Kill 장부는 실패한 미완료 Wave에서 실제로 발생한 처치까지 보존한다.

## Integration Blocker — Spring canonical Kill 검증 충돌

현재 Spring `BattleSettlementService`는 다음 방식으로 요청을 검증한다.

```text
expectedKills = expectedKillsThrough(request.finalWave)
submitted monsterKills == expectedKills
```

`expectedKillsThrough(finalWave)`는 Wave 1부터 마지막 완전 클리어 Wave까지만 모든 canonical Spawn이 처치됐다고 계산한다. 따라서 Wave 70 진행 중 실패해 `finalWave=69`이면서 Wave 70 Monster 일부를 실제로 처치한 정상 Summary는 제출 Kill이 예상값보다 많아져 `BATTLE_SUMMARY_INVALID`로 거절된다.

이는 확정된 P2-3-2 정책인 “FAILED 미완료 Wave의 실제 Kill/Support Kill도 Quest에 포함”과 충돌한다. Battle 쪽에서 실제 Kill을 버려 우회하면 안 된다. User/System + Server 담당이 Settlement 신뢰 검증을 다음 두 사실로 분리하는 계약을 먼저 확정해야 한다.

- 완전 클리어 Wave 검증: `finalWave` 기준 canonical 완료 여부
- 미완료 진행 Wave Kill 검증: State Authority가 제출한 실제 Kill 장부를 신뢰할 서버 권위 증거

이 차단이 해결되고 `QuestSettlementProcessor`, trusted `Session Source=PRODUCTION`, 멱등 키가 서버에 구현되기 전에는 P2-3-2 production E2E를 완료로 판정할 수 없다.

## 제외 범위

- `QuestSettlementProcessor`
- Session Source (`PRODUCTION`, `LOCAL_DEVELOPMENT`, `VALIDATION_FIXTURE`)
- `P1VAL`/Fixture 영구 진행 차단
- `SERVER_ABORTED`
- production JWT/matchmaking roster adapter
- Quest 조건·보상·영속화·멱등 처리
- 실시간 Quest UI 및 Shared 이벤트 DTO

위 항목은 User/System + Shared + Server 소유이며 Battle에서 우회 구현하지 않는다.

## 후속 검증

1. Server 담당이 FAILED partial-wave Kill을 수용하는 신뢰 계약과 테스트를 구현한다.
2. `QuestSettlementProcessor`가 `settlementId + userId + questConditionId`로 정확히 한 번만 반영하는지 검증한다.
3. 같은 PRODUCTION 2인 Session에서 실제 Settlement 승인 후 Quest 저장값을 재조회한다.
4. 재전송·서버 재시작·동시 요청에서 Quest 진행이 중복되지 않는지 E2E로 확인한다.
